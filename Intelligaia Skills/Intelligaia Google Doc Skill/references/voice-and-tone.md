# Voice & tone

Intelligaia "humanizes AI for enterprises." The writing is **confident, plain, and specific** —
the voice of a senior practitioner, not a marketing department. It respects the reader's time.

## Core voice (all doc types)

- **Lead with the point.** First sentence of any section states the takeaway; the rest supports it.
- **Concrete over abstract.** Name the thing, the number, the mechanism. Avoid "leverage synergies,"
  "cutting-edge," "seamless," "revolutionary," "world-class," "robust," "next-gen."
- **Short declarative sentences.** One idea per sentence. Prefer active voice.
- **Confident, not boastful.** State what is true. Do not oversell; do not hedge with "we believe we
  might be able to."
- **Reader-second-person for guidance**, Intelligaia-first-person for commitments ("You'll see… / We
  deliver…"). Never slip into breathless third-person about the brand.
- **Sentence case** in titles, headings, and body. No ALL-CAPS except small labels/eyebrows.
- **Gold is the accent for every doc type** — there is no blue/purple choice (that's the website
  system). Types differ by *density, structure, and how much gold furniture they carry*, not by hue.
- **Never invent proof.** No metric, client name, testimonial, date, fee, or outcome that the user
  did not supply. Mark a gap `[TK: metric]` rather than filling it. (Hard rule — see guardrails.)

## Tone dial per doc type

The house voice is constant; the **density, structure, and typographic emphasis** change. These are
the "variables" the skill flexes.

| | Description doc | Proposal doc | Architecture / diagram doc | Q&A doc |
|---|---|---|---|---|
| **Purpose** | Explain a product/service/solution in narrative form | Win/scope client work | Communicate a technical design | Answer a defined set of questions |
| **Reader** | Mixed; often non-technical | Client decision-makers | Engineers, technical leads | Anyone; reference use |
| **Wording density** | **Higher** — full paragraphs, narrative flow | **Lower** — tight, scannable, whitespace | Medium — prose + specs + tables | Low per item; many items |
| **Sentence length** | Medium, can breathe | Short, punchy | Short; precise, unambiguous | Short answers, 1–4 sentences |
| **Signature emphasis** | Lede + generous body; restrained gold | Eyebrows, gold callouts, one hero stat | Component tables, mono for specs; gold sparingly | Question in Montserrat SemiBold, hairline-separated |
| **Structure bias** | Sections of prose, few bullets | Bullets, callouts, a table, clear CTA | Component tables, figure + caption, sequence | Repeating Q→A blocks, optional grouping |
| **Length target** | 2–5 pages | 3–8 pages | 2–6 pages | 1–4 pages (scales with #questions) |
| **Jargon** | Explain terms | Minimal; benefit-led | Precise technical terms expected | Match the question's register |

**Rule of thumb the model follows when drafting:** a *description* reads like a good explainer; a
*proposal* reads like a sharp one-pager that happens to run a few pages; an *architecture* doc reads
like a spec a developer can build from; a *Q&A* reads like a crisp FAQ. If a draft for one type starts
feeling like another (a proposal ballooning into narrative prose, a description turning into terse
bullets), it has drifted — pull it back to the row above.

## Openings (patterns, not templates — never lorem ipsum)

- Description: one-sentence definition of what the thing *is*, then why it matters to the reader.
- Proposal: the client's problem in their words, then the outcome Intelligaia will deliver.
- Architecture: the system's job in one line, then its shape (major components) before any detail.
- Q&A: a one-line scope note ("Answers to the questions raised in <context>"), then straight into Q1.
