# Design Opportunity Prioritization & Validation

## 1. Prioritization Inputs
Evaluate:
evidence strength → user consequence → business consequence → reach → integrity/risk → strategic alignment → dependency → implementation uncertainty.

Do not invent scores where no scoring model exists.

## 2. Opportunity Portfolio
Group into:
foundational/enabling → journey improvement → risk/control → efficiency → strategic/transformational.

A foundational data/integration fix may enable several visible UX improvements.

## 3. Dependency First
Before prioritizing a UI change, identify whether success depends on:
catalog → pricing → approval policy → data quality → API/integration → lifecycle model → authorization → platform → operating model.

## 4. Feasibility
Validate technical feasibility with architecture/platform owners rather than assuming a design can be implemented.

## 5. Desirability
Validate with relevant roles and scenarios. Include new/expert sellers, approvers, operations, partners or lifecycle users as appropriate.

## 6. Viability
Check policy, commercial, support, compliance, channel and operating-model implications.

## 7. Prototype
Prototype the smallest representation needed to test the key assumption.

Do not build high-fidelity screens merely to validate a workflow concept.

## 8. Scenario Testing
Use realistic CPQ scenarios:
new business; complex bundle; discount approval; revision; large quote; downstream failure; amendment; renewal; partner sale.

## 9. Edge Cases
Include:
stale version; expired price; pending approval; timeout; partial success; pending amendment; role change; unauthorized data.

## 10. Success Evidence
Define evidence before testing:
completion → comprehension → error avoidance → recovery → time/effort → confidence → downstream quality.

## 11. Baseline
Use an actual current-state baseline where available. If absent, state that improvement cannot yet be quantified.

## 12. Guardrail Metrics
Ensure optimization does not increase:
commercial errors; invalid configurations; approval bypass; duplicate orders; billing fallout; security exposure.

## 13. Pilot
For material workflow changes, consider controlled pilot with defined users/scenarios, support path and measurement.

## 14. Feedback
Separate preference (“I like it”) from demonstrated task success and business outcome.

## 15. Iterate
Update:
finding → root-cause confidence → opportunity → pattern → requirement → metric.

## 16. Decision Record
For major opportunities capture:
evidence → alternatives → chosen direction → dependencies → risks → validation result → decision owner/date.

## 17. Roadmap
Sequence enabling work before dependent experience work.

## 18. Benefits
Keep benefits as:
validated → modeled/estimated → hypothesis.

Do not present estimated savings or revenue as fact.

## Guardrail
Do not invent feasibility, effort, ROI, adoption, metric baselines, targets or research results.
