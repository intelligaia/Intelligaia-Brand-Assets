# Seller Experience — Approvals, Customer & Downstream Handoffs

## 1. Approval Submission
Before submission:
validate required state → summarize approval drivers → identify exact quote/version → collect rationale → submit.

## 2. Pending Approval
Seller needs:
status → current owner/stage where appropriate → submitted version → elapsed context → permitted actions.

## 3. Approval Change
If seller edits a material commercial field:
explain whether approval remains valid → requires resubmission → is blocked while pending.

## 4. Rejection
Return:
reason → affected commercial condition → required correction → route back to same quote/version context.

## 5. Customer Handoff
Customer-facing quote/proposal should remain correlated to the governed source version.

## 6. Customer Change Request
Capture requested change → create/revise governed commercial state → compare delta → reprice/revalidate/reapprove as required.

## 7. Acceptance
Make it clear which version was accepted and prevent later drafts from being mistaken for accepted commercial intent.

## 8. Order Readiness
Before downstream commitment show unresolved blockers:
approval → acceptance → configuration → pricing → required data → date/term → policy.

## 9. Submission
Submission should provide a stable business reference and prevent accidental duplicate clicks/replays.

## 10. Processing
For asynchronous handoff:
submitted ≠ completed.

Show pending/processing and allow safe status retrieval.

## 11. Partial Completion
If some order/components succeed:
show completed/pending/failed → seller/customer impact → owner → safe next action.

## 12. Failure
Business-facing error:
what failed → what remains safe → whether seller action is possible → support/correlation reference.

## 13. Unknown Outcome
Prevent blind resubmission when the target outcome is uncertain.

## 14. Completion
Show relevant order/subscription/downstream reference and resulting business status.

## 15. Operations Handoff
When support/operations takes over, preserve:
customer/deal → quote/version → operation → error/status → seller/customer commitment context.

## 16. Return to Seller
After operations correction, seller should see updated business state without reconstructing the transaction.

## 17. Notifications
Use notifications for meaningful state changes requiring awareness/action, not every technical event.

Exact channels/cadence require evidence.

## 18. Audit
Seller-facing history should focus on meaningful commercial decisions and handoffs; detailed technical logs belong in operational diagnostics.

## Evaluation Questions
- Is the submitted/accepted version unambiguous?
- Can sellers see why approval is required?
- Does rejection return them to the right work?
- Can duplicate downstream submission occur?
- Are pending and completed states distinct?
- Can sellers recover from failure without recreating the quote?

## Guardrail
Do not invent approval stages, notification channels, customer acceptance mechanisms, downstream statuses, retries or support ownership.
