# Comparative Patterns

## Pattern Classes
The following are **investigation lenses**, not customer claims.

### `COMP-PAT-001` — Commerce / CPQ experience simplification
Use case-study UX/process evidence to ask whether users face excessive navigation, unclear state, avoidable manual work or poor decision visibility.

### `COMP-PAT-002` — Partner / channel transaction complexity
Use partner/distributor case evidence to investigate actor-specific workflows, handoffs, entitlement/visibility and exception handling.

### `COMP-PAT-003` — Cross-system commerce handoffs
Use case evidence to investigate where quote/order/subscription/billing state crosses system boundaries and where ownership or recovery becomes unclear.

### `COMP-PAT-004` — Product / catalog / configuration usability
Use reference implementations to investigate discoverability, configuration guidance, validation and commercial context. Do not infer the target customer needs the same UI.

### `COMP-PAT-005` — Lifecycle / post-sale change experience
Use amendment/renewal/cancellation examples to investigate authoritative state, effective dates, downstream consequences and reconciliation.

### `COMP-PAT-006` — Analytics / operational visibility
Use analytics examples to investigate what decisions users cannot make today because required state, status or consequence is not visible.

## Runtime Use
A comparative pattern should generate a **question or hypothesis first**.

Correct:
`Reference pattern → investigate target evidence → validate target problem → derive target story/recommendation`

Incorrect:
`Reference solution → recommend same solution to target`
